# Kip subagent roles

Use these briefs to scope the worker and reviewer handoffs in a [Kip squad](squads.md). Attach only the brief and project guidance relevant to the assignment. The current host adapter selects the native tool, and the effective profile supplies settings for the slot. These roles work through transient handoffs in the current session. See the [orchestration contract](orchestration.md).

## Assign roles to existing slots

Solo keeps applicable duties with the root. Lean uses one worker and a separate independent reviewer. Full can give a second worker a disjoint implementation or verification scope. Combine several duties in the same assignment when they share evidence or depend on one another. Use the audit adapter for `audit`.

| ----------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Plan writer             | Root, with source mapping from a worker in a delegated `plan` | Map requirements to acceptance checks and existing code. Keep drafts in chat for `plan`.                                                                                                                             |
| Plan reviewer           | Independent reviewer for `plan`                               | Check the draft against the request and source. Identify narrower options using existing code or platform features, missing acceptance checks, and dependencies that make proposed parallel work unsafe.                                                                                                                           |
| Builder                 | Implementation worker                                         | Work within the owned paths. Prove uncertain feasibility in a disposable spike when authorized. Apply TDD when requested or required by the project. Return changed paths, checks actually run, and unresolved issues. [Spike](engineering/spike.md), [TDD](engineering/tdd.md)                                                    |
| Correctness             | Review worker or independent reviewer                         | Trace each requirement through the relevant entry point. Check compatibility and whether the relevant test would catch a plausible regression. ## Run an independent review

Send the reviewer requirements and acceptance criteria, project path and exact review scope, applicable project instructions, and locations of any test recipe or results. Identify the base and worktree changes, including staged, unstaged, or relevant new files. For rechecks, include prior findings and the scope of the fix. Share objective results and known limits. The reviewer checks the source and evidence independently of the builder's conclusions.

Apply correctness, edge-case, and complexity lenses within the existing slots. To report a blocking finding, give a file and line or failed required check, the triggering input or state, the consequence, and a fix direction. Run focused checks only within the task's execution permissions. `plan` and source-only `review` inspect existing material. Workers and reviewers preserve the assigned boundary and send their findings back to the root.
