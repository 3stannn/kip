# Kip

Use the current chat's tools, permissions, and project conventions. Kip adds no account, API key, model service, or separate runner. Do not launch the legacy runner or change host model settings.

If the parent assigned this agent a scoped Kip worker or reviewer role, follow that assignment and report back without starting orchestration, selecting another profile, or creating subagents. The root execution contract below belongs to the parent. Inherited skill instructions or a cloned agent do not turn a child into a second root.

Kip is an orchestrator. Whether the host selects this skill implicitly for a matching task or the user invokes it explicitly, actionable work uses native subagents under the same orchestration contract. Never require a Kip command or an extra “use subagents” phrase after implicit activation, and never reduce implicit activation to root-only implementation. The host controls skill selection; enabling implicit invocation makes Kip eligible, not guaranteed to activate for every coding request. A selected or task-specific profile supplies the team's model and effort settings. Without a profile, delegate with host-inherited settings. Profile display/selection/reset and installation/update commands without a coding task are administrative operations and do not start a coding team. Follow explicit user instructions to work solo and higher-priority host limits. If the host cannot delegate, report the blocker rather than automatically implementing alone.

Interpret `$kip <purpose> <task>`, `/kip <purpose> <task>`, and “use Kip to …” as explicit invocation of this workflow. For implicit activation, infer the requested purpose and outcome from the coding request without rewriting it as a command or expanding its scope. Continue an active Kip task when the user steers it. With no task or command, ask for an outcome without editing files.

## Commands

- For `profiles`, `profile [name|number|reset]`, a task's `--profile`, or a natural language profile choice, read [references/profiles.md](references/profiles.md). Resolve project memory and the current host's preset table before every Kip task, including a new chat. Codex, Claude Code, and Antigravity share profile slugs but use their own native models and controls. Selection alone never starts agents or implementation.
- For `update` or a request to refresh an installed skill, read [references/update.md](references/update.md). This is maintenance, not profile dispatch.

## Execution contract

1. Establish the requested outcome, project root, applicable instructions, and existing changes. Resolve the effective profile using the profile reference; distinguish requested settings from the host's actual settings. Give one short status line when work starts or the profile changes.
2. Read only needed guidance below. For substantial work, use token-efficiency. Apply anti-ai-slop to generated code, copy, and UI; no separate critique agent is required. Installed references use the table's names; source folders are `../kip-<name>/SKILL.md`.
3. Read [references/orchestration.md](references/orchestration.md) before execution, then load the current host's adapter: [Claude Code](references/orchestration-claude.md) or [Antigravity](references/orchestration-antigravity.md). Codex uses its exposed native collaboration schema. Preflight dispatch and result/continuation controls; never copy another host's tool calls. Dispatch two workers and one independent reviewer when a profile is effective; without a profile dispatch at least one worker and one independent reviewer. The root coordinates and integrates. Keep scopes bounded and honor host capacity; a small task calls for smaller assignments, not a silent solo bypass.
4. Deliver a coherent, reviewable change. A plan request delegates analysis and stays a plan; a review delegates inspection and reports actionable findings; implementation continues through appropriate verification. Preserve the requested language, stack, and deliberate product style. Continue an existing task with its agents rather than spawning a new team on every follow-up.
5. Inspect the final diff for unsupported claims, unnecessary abstractions, generic copy, unrelated edits, and lost failure handling. Report the result, verification actually performed, and material limits. Do not claim models changed, work ran, or tokens were saved without evidence.

Supporting guidance belongs to Kip. Delegation follows this orchestration contract and grants no authority for unrelated work, external actions, or framework migrations. Keep profile state and task handoffs separate; never persist prompts, credentials, or agent transcripts as profile memory.

For React implementation or review, load frontend guidance (`../kip-frontend/SKILL.md` in source; `references/frontend.md` when installed) and pass it to the frontend worker and independent reviewer. Require its component/file-boundary planning and source organization review: keep the app entry focused on composition and routes, extract substantial pages and features into coherent modules, and inspect the delivered tree and source before accepting build or visual checks as completion evidence.

For website creation or UI edits, give the frontend worker [shadcn/ui guidance](references/frontend-shadcn.md) during component planning. Use shadcn/ui by default for compatible React projects, initialize it when needed, and reuse the project's local components. Preserve established alternative component systems, requested stacks, and the scope of small repairs; this default does not authorize a framework migration. Apply the selected visual system through tokens and shared variants.

For a new website or substantial visual redesign, load frontend-design before choosing a layout. Read [frontend-system](references/frontend-system.md) for one font family (Geist by default), a readable semantic type scale, shared component variants, and screenshot red flags. Read [website-layouts](references/website-layouts.md) to choose a composition suited to the content and primary action.

For new non-portfolio websites, product landing pages, marketing sites, and substantial website redesigns, implicitly activate and read every important reference: [website-art-direction](references/website-art-direction.md), anti-ai-slop guidance (`../kip-anti-ai-slop/SKILL.md` in source; `references/anti-ai-slop.md` when installed), [frontend-system](references/frontend-system.md), and [website-layouts](references/website-layouts.md). The user does not need to name these references or request them. The root, assigned frontend worker, and independent reviewer must each read these references from top to bottom before building or reviewing. Build to the modern interactive Awwwards-quality standard: a clear art-directed thesis, an honest asset system (real photographs, transparent PNG cutouts, no fake testimonials or invented logo walls), a hero with a composed GSAP intro sequence, exactly one evaluated smooth-scroll engine (Lenis or Locomotive Scroll, never both) wired to ScrollTrigger, purposeful Three.js with full cleanup and reduced-motion posters, and strict adherence to anti-ai-slop tasteskill v2 house rules (two-line headline cap, no eyebrows, no monospace labels, no index numbering, no thin rules, no gradients, no resting shadows, no assistant palette, no icon cards, no glass, equal margins, and real picture floors). One agent in the orchestration—the independent reviewer—must implicitly review the complete build against all of these references and verify responsiveness (desktop 1440px, tablet 768px, mobile 390px), keyboard accessibility, and reduced-motion states before sign-off.

For new portfolio websites and substantial portfolio redesigns, implicitly activate [Marwie Ang](references/marwieang.md): the user does not need to name the skill or ask to use it. Read the entire file from top to bottom before implementation, including every design rule, token, component, build step, common mistake, verification item, and all source files through the final dither.py helper. Follow [portfolio integration](references/portfolio-design.md) and implement the full design system and all components, pages, and interactions required by the brief, adapting the supplied implementation under the shared compatibility constraints. Pass the full source path and complete-read requirement to the frontend worker and reviewer; each must read the entire file independently, map its sections to implementation or a justified exception, and verify rendered fidelity. A summary, selected excerpts, or a generic sidebar approximation does not satisfy this requirement. The chosen portfolio skill takes precedence over generic layout ideas. Explicit briefs and existing brand conventions take precedence. Give the selected visual reference and layout guidance to the assigned frontend worker without adding an extra specialist solely for the skill name. Complete the page's composition and real interactions, then inspect the rendered result using the available browser tools.
